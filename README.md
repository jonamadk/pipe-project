# PIPE — Retrieval-Grounded Plumbing Safety Q&A (Prototype)

A working demo of turning PIPE's rule-based plumbing-safety engine into a
retrieval-grounded Q&A system, built from two real guidance papers (Singh
et al., 2020 and 2022, *Water* journal). It implements **five** interchangeable
retrieval strategies, plus a Python evaluation harness that scores all five
against a 50-question gold set:

| Strategy | Idea | When it's the right call |
|---|---|---|
| **TF-IDF vector search** | Classic bag-of-words similarity over all passages | Default baseline RAG |
| **GraphRAG** | Traverse a small hand-built knowledge graph of entities/relations | Multi-hop questions where wording doesn't match source text |
| **Long-context prompting** | Skip retrieval; hand over the whole corpus every time | Corpus small enough to fit the context window |
| **Memory compression** | Search a pre-summarized digest, not raw passages | Corpus too large to search/pass around cheaply |
| **Structured retrieval** | Classify the question, route to an exact table lookup, else fall back to vector search | Query types vary and some have a known, exact-answer shape |

Every strategy feeds into the same generation step, under a strict "answer
only from what you retrieved" system prompt.

This is a prototype for demonstrating the architecture end-to-end, not a
production deployment. See "Moving to production" below for what changes.

## Source document repo (Google Drive)

The two guidance papers' canonical source is this Google Drive folder:
https://drive.google.com/drive/folders/1BlwpAZjQfHkUkPoLQXEiFY5ugBCstdE8

`data/raw/manifest.json` links each `data/raw/docN_raw.txt` to the Drive
file it came from (`driveFileId`, `driveTitle`, `driveModifiedTime`).
`scripts/chunk_documents.py` reads its document list from this manifest —
not a hardcoded list — so registering a new document only requires an
entry there, no code changes.

To pull in a new or changed file from that Drive folder, ask Claude to
sync the knowledge base from Drive (or run `/sync-pipe-drive`) — this is a
manual, on-request sync (no standing automation) that follows the
procedure in `.claude/skills/sync-pipe-drive/SKILL.md`: list the folder,
diff against the manifest, normalize and save any new/changed file into
`data/raw/`, update the manifest, and rebuild the corpus. Note that
`kg.json`, `structured_facts.json`, and `compressed_summary.json` stay
hand-curated and are **not** auto-extended for a newly synced document —
see "Adding more guidance documents" below.

## Running the full-stack version (Python backend + React frontend)

The primary way to run this app is now a FastAPI backend serving retrieval
+ generation, with a separate Vite/React frontend — this replaces the
single-file client-side app's generation step with a real backend, and
adds OpenAI as an alternative to Anthropic for the generation call.

```bash
# Backend (FastAPI) — from backend/
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn main:app --reload --port 8000

# Frontend (React + Vite) — from frontend/, in a second terminal
npm install
npm run dev
```

Then open `http://localhost:5173`. All five retrieval strategies
(`backend/../scripts/retrieval_methods.py`) now run server-side in Python
instead of duplicated JS; the frontend just renders whatever the backend
returns. Pick Anthropic or OpenAI from the dropdown in the top bar and
paste in your API key — it's kept in the browser's `localStorage` and sent
to your own local backend on each question, never persisted server-side.
The backend calls `https://api.anthropic.com` or `https://api.openai.com`
using each provider's official SDK, standing in for the local LLM a
production deployment would run on-prem.

`frontend/.env.example` shows the `VITE_API_BASE_URL` override if you run
the backend somewhere other than `http://localhost:8000`.

### Basic PIPE Assessment Form

The sidebar's "Basic PIPE Assessment Form" button opens the 18-question
building intake form from PIPE's public decision-support tool (grouped
into Building Plumbing System Monitoring, General Water Devices, Critical
Water Devices, and Building/Facility Type). Submitting it doesn't run a
locally-invented scoring rubric — it POSTs the answers to
`backend/main.py`'s `/api/assess` endpoint, which:

1. Grounds the 4 questions that map to an exact parameter in
   `data/structured_facts.json` (`QUESTION_TO_STRUCTURED_PARAM` in
   `backend/constants.py`: point-of-use temperature, time to tap, residual
   disinfectant, water heater setpoint) in those exact guidance records.
2. Runs TF-IDF retrieval (`k=12`) over the rest of the profile (dead legs,
   high-risk devices, vulnerable populations, building complexity) to pull
   in the relevant guidance excerpts for those.
3. Sends the full building profile plus both sets of guidance to the
   selected LLM provider (`backend/prompts.py`'s `build_assessment_prompt`)
   to produce a cited report: overall water-management-plan determination,
   flagged factors with citations, and recommended next steps.

The report appears as a normal message in the chat thread (mode
"Building Assessment"), with a sources panel showing the submitted
profile, the exact parameter records used, and the retrieved excerpts —
same transparency model as the regular chat modes.

## Running the evaluation

```bash
python scripts/evaluate.py
```

This scores all five retrieval strategies against the 50 questions in
`data/qa_eval_set.json`, entirely offline — no API key, no network call,
fully deterministic. For each method it reports:

- **Hit@k** — did the retrieved context contain at least one gold source chunk?
- **Recall** — what fraction of the gold source chunks were retrieved?
- **Precision** — what fraction of the retrieved chunks were actually relevant?
- **Context size** — how many chunks/words were handed to the LLM (the cost side of the tradeoff)

...plus a recall breakdown by question category, and the full per-question
detail written to `data/eval_results.json`.

Sample output from this build:

```
Method           Hit@k   Recall  Precision   Avg ctx (chunks)   Avg ctx (words)
--------------------------------------------------------------------------------
vector           0.960    0.903      0.237                4.9             726.1
graph            0.440    0.430      0.071                5.8             997.7
long_context     1.000    1.000      0.034               39.0            4973.0
compressed       0.940    0.930      0.134                9.6             257.7
structured       0.880    0.823      0.353                3.6             442.3
```

The most important, and least obvious, finding: **GraphRAG does not
out-recall vector search across the board.** It only performs well on
question categories its 25-entity graph actually models (materials,
temperature); on categories with no matching entities (guidance landscape,
knowledge gaps) its recall is 0. This is an honest illustration that a
knowledge graph's value is bounded by how much of the domain got modeled
as entities and relations — it is not a free upgrade over text search.
`structured` gets the highest precision of any method (exact table lookups
have no false positives), and `long_context` gets perfect recall by
construction but the worst precision and by far the largest context size —
the token-cost tradeoff that "just use a bigger context window" glosses over.

### Optional: end-to-end generation + LLM judging

The metrics above test *retrieval* quality only. To also test the full
pipeline — actually generating an answer and grading it against the gold
answer — set `ANTHROPIC_API_KEY` in your environment and add `--generate`:

```bash
export ANTHROPIC_API_KEY=sk-...
python scripts/evaluate.py --generate --sample 15   # sample of 15 questions (default)
python scripts/evaluate.py --generate --full        # all 50 questions (costs more)
```

This calls the Anthropic API twice per question per method (once to
generate, once to have Claude judge the generated answer against the gold
answer on a 0-2 scale) using only Python's standard library — no extra
pip dependencies. This step needs real API access and was not run inside
the sandbox this project was built in; the retrieval-only metrics above
are what's been verified end-to-end.

## How retrieval works

**TF-IDF vector search** (`retrieval_methods.py::vector_retrieve`, mirrored
in JS as `tokenize`/`vectorize`/`cosineSim`/`retrieve`): classic bag-of-words
statistical retrieval. A vocabulary and inverse-document-frequency weight
are built once from all 39 chunks; each question is vectorized the same
way and scored by cosine similarity against every chunk. No embeddings
model, no network call.

**GraphRAG** (`retrieval_methods.py::graph_retrieve`, mirrored in JS as
`matchEntities`/`graphRetrieve`): a small hand-built knowledge graph
(`data/kg.json` — 25 entities, 29 relations) sits alongside the text
chunks. Entities mentioned in a question are matched by alias, then the
graph is traversed up to 2 hops out, collecting relation triples and
their supporting chunk citations. This surfaces connections that pure
text similarity misses — e.g. linking "PVC pipe" to "Legionella" to
"water heater setpoint" as one path — but see the evaluation results
above for its real limitation: it only works within what's been modeled.

**Long-context prompting** (`retrieval_methods.py::long_context_retrieve`,
JS `longContextRetrieve`): no retrieval step. All 39 chunks (~5,000 words)
are handed to the model on every question. Perfect recall by construction,
at the cost of the largest context size and lowest precision of any method.

**Memory compression** (`retrieval_methods.py::compressed_retrieve`, JS
`compressedRetrieve`): a hand-written 10-entry digest
(`data/compressed_summary.json`) condenses the corpus into dense
topic summaries, each citing the original chunks it's built from. A
question is keyword-matched against the digest (a much smaller search
space than the 39 raw chunks), and the matched digest entries plus their
cited original chunks are handed to the model together — the digest for
fluent framing, the original excerpts for precise numbers.

**Structured retrieval** (`retrieval_methods.py::structured_retrieve`, JS
`structuredRetrieve`/`classifyParameter`): a 9-parameter lookup table
(`data/structured_facts.json`, built from Table 4 in both papers) maps
known parameter names/aliases (water heater setpoint, POU temperature,
flushing frequency, etc.) to their exact guidance and survey records. If
a question names a known parameter, it gets those exact records with no
fuzzy matching at all; otherwise it falls back to TF-IDF vector search.

Every mode hands its results to Claude under a strict system prompt (see
`SYSTEM_PROMPT_TEMPLATE` / `buildGraphPrompt` / `buildLongContextPrompt` /
`buildCompressedPrompt` / `buildStructuredPrompt` in the template):
answer only from what was retrieved, cite document + page for every
claim, and say so explicitly rather than guessing if the question isn't
covered.

## Adding more guidance documents

1. Extract the document's text (any PDF-to-text tool works) and clean it
   up, inserting `[Page N]` or `[Page N-M]` markers wherever a new page
   starts. See `data/raw/doc1_raw.txt` for the expected format.
2. Save it as `data/raw/docN_raw.txt`.
3. Add an entry to `DOCS` in `scripts/chunk_documents.py` (id, title,
   short label, path).
4. Optionally extend `data/kg.json` (via `scripts/build_knowledge_graph.py`)
   with new entities/relations, `data/structured_facts.json` (via
   `scripts/build_alt_retrieval_data.py`) with new parameters, and
   `data/compressed_summary.json` with new digest entries — all citing the
   new chunk ids. In production this extraction would be automated (an
   LLM pass proposes candidates, a human reviews before merge); this
   prototype keeps it manual so everything stays small enough to audit
   directly.
5. Add new questions to `data/qa_eval_set.json` covering the new material,
   so `evaluate.py` keeps measuring real coverage rather than stale ground truth.
6. Re-run `python scripts/build_app.py` and `python scripts/evaluate.py`.
7. Add the new document to `DOC_META` in `app/template.html` so it shows
   up in the sidebar.

## Moving to production

This prototype intentionally swaps out two things that a real PIPE
deployment would do differently, both noted in the "How this demo works"
panel inside the app itself:

- **Generation**: replace the `fetch("https://api.anthropic.com/v1/messages", ...)`
  call in `askClaude()` with a call to a local model server (e.g. an
  Ollama or vLLM endpoint running on-prem), keeping the same system
  prompt structure. The retrieval-then-generate flow doesn't change —
  only where the generation call goes.
- **Entity/relation extraction for the knowledge graph**: currently
  hand-curated in `build_knowledge_graph.py`. In production this would
  be an automated ingestion step (LLM-assisted extraction + human
  review) so the graph grows as new guidance documents are added,
  rather than requiring a person to write graph edges by hand.

Everything else — the chunking approach, the TF-IDF retrieval, the
citation-and-refusal discipline in the system prompt — is representative
of the production design, just running at a two-document scale instead
of a full corpus.

## Known limitations of this prototype

- The two source documents were extracted from Google Drive as
  natural-language text (not a raw PDF parse), so page boundaries are
  approximate in a few places where the extraction merged short pages.
- The 5 retrieval modes are separate strategies, not blended — you pick
  one per question. A production system might combine them (e.g. graph
  traversal to expand a text-similarity result set, or structured lookup
  as a pre-filter before vector search on the remainder).
- The knowledge graph, structured facts table, and compressed digest are
  all hand-curated from these two papers specifically. None of them are
  automatically kept in sync if you add new raw documents without also
  updating the corresponding build script (see "Adding more guidance
  documents" above).
- The 50-question gold set was written by hand alongside the source
  documents, so its "gold chunk" labels reflect one reasonable judgment
  of relevance, not a blind human-annotation process. Retrieval scores
  should be read as internally comparative (which method does better
  than which, on this corpus) rather than as absolute quality numbers.
- `evaluate.py`'s generation+judging path (`--generate`) has not been run
  end-to-end in the environment this project was built in, since it has
  no `ANTHROPIC_API_KEY` configured. The retrieval-only metrics have been
  verified and are what the README's sample output reflects.
